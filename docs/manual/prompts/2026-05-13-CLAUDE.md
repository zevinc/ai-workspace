## 二、强制规范 (Mandatory Standards)

### 2.1 项目结构

```
src/main/java/com/example/project/
├── common/          # 公共类：常量、异常、工具类
├── config/          # @Configuration 配置类
├── controller/      # REST Controller（薄层，不放业务逻辑）
├── service/
│   ├── impl/        # Service 实现
│   └── xxxService.java  # 接口
├── mapper/          # MyBatis Mapper 接口
├── model/
│   ├── entity/      # 数据库实体（禁止暴露到 Controller）
│   ├── dto/         # 入参 DTO（以 Request/Query/Cmd 结尾）
│   ├── vo/          # 出参 VO（以 VO 结尾）
│   └── converter/   # MapStruct Converter 接口
├── enums/           # 枚举类
├── exception/       # 自定义异常
└── util/            # 项目级工具类（Hutool 补充不了的）
```

**规则：**
- Controller 禁止包含任何业务逻辑，只能做参数校验 + 调用 Service + 返回结果
- Entity 禁止暴露到 Controller 层，必须经过 Converter 转为 VO
- Service 层必须定义接口（`XxxService`），impl 实现（`XxxServiceImpl`）
- 每个模块根包名统一，禁止随意建包

### 2.2 命名规范

| 类型 | 规则 | 示例 |
|------|------|------|
| Controller | `{业务}Controller` | `UserController` |
| Service 接口 | `{业务}Service` | `UserService` |
| Service 实现 | `{业务}ServiceImpl` | `UserServiceImpl` |
| Mapper | `{Entity}Mapper` | `UserMapper` |
| Entity | 与表名对应（下划线转驼峰） | `User`, `OrderItem` |
| DTO | `{操作}{对象}Request/Query/Cmd` | `UserCreateRequest`, `OrderQuery` |
| VO | `{对象}VO` | `UserVO`, `OrderDetailVO` |
| Enum | 业务含义名 | `OrderStatus`, `UserType` |
| Exception | `{场景}Exception` | `UserNotFoundException`, `BizException` |
| Converter | `{Entity}Converter` | `UserConverter` |
| REST URL | `/api/v{1}/{resource}` | `/api/v1/users` |
| REST 方法 | 复数名词，CRUD 用 HTTP 方法区分 | `GET /users`, `POST /users` |
| 数据库表 | 小写 + 下划线，单数 | `user`, `order_item` |
| 数据库列 | 小写 + 下划线 | `created_at`, `order_status` |

### 2.3 代码质量硬性规则

```
1. 所有 public 方法必须有 Javadoc（至少 @param + @return + @throws）
2. 所有 DTO/VO 字段必须加 @Schema(description = "...") 注解
3. 所有 Controller 方法必须加 @Operation(summary = "...") 注解
4. 禁止方法超过 80 行（超过必须拆分）
5. 禁止类超过 500 行（超过必须拆模块）
6. 禁止方法参数超过 5 个（用 DTO 封装）
7. 禁止圈复杂度超过 10（超过必须重构）
8. 禁止写注释来解释「为什么代码这么烂」，如果代码烂就重构
9. 日志必须用 {} 占位符，禁止字符串拼接
10. 禁止在循环中使用 + 拼接字符串（用 StringBuilder）
```

### 2.4 参数校验规范

```java
// ✅ 正确
@PostMapping("/users")
public Result<UserVO> create(@Valid @RequestBody UserCreateRequest request) {
    // ...
}

public class UserCreateRequest {
    @NotBlank(message = "用户名不能为空")
    @Size(min = 2, max = 20, message = "用户名长度2-20")
    private String username;

    @NotBlank
    @Email(message = "邮箱格式不正确")
    private String email;

    @NotNull
    @Min(value = 1, message = "年龄不能小于1")
    @Max(value = 150)
    private Integer age;
}
```

**规则：**
- Controller 入参必须用 `@Valid` / `@Validated`
- DTO 字段必须用 Jakarta Validation 注解（`@NotNull`, `@NotBlank`, `@Size` 等）
- 禁止在 Controller 方法体内手动校验参数
- 自定义校验逻辑写为自定义 Validator + 注解
- 分组校验用 `@Validated` 的 groups 机制，不要写 if-else

### 2.5 测试强制要求

```
1. Service 层单元测试覆盖率 ≥ 80%
2. Controller 层必须有 @WebMvcTest 集成测试
3. 数据库 Mapper 必须有 @MybatisTest 或 @DataJpaTest
4. 关键业务流程必须有 Testcontainers 端到端测试
5. 测试类命名: {被测类}Test（如 UserServiceTest）
6. 测试方法命名: should_{预期行为}_when_{条件}（如 should_throwException_when_userNotFound）
7. 所有断言必须用 AssertJ（assertThat(...).isEqualTo(...)），禁止用 JUnit 断言
8. 禁止测试用例之间有依赖（顺序无关）
```

### 2.6 配置管理

```
1. 敏感信息（密码、密钥）禁止写在 application.yml → 必须用环境变量或配置中心
2. 多环境配置: application-{profile}.yml（dev/test/staging/prod）
3. 禁止硬编码 IP、端口、URL → 必须用 @ConfigurationProperties
4. 业务常量统一放 Constants 类，禁止魔法值
5. 配置属性类必须加 @Validated + Jakarta Validation 注解校验
```

### 2.7 Git 提交规范

```
格式: <type>(<scope>): <subject>

type: feat | fix | refactor | docs | test | chore | perf | style
scope: 模块名（如 user, order, payment）
subject: 中文描述，≤72 字符，不以句号结尾

示例:
feat(user): 新增用户注册接口
fix(order): 修复并发下单库存超卖问题
refactor(payment): 重构支付回调幂等逻辑

禁止:
- 一次提交包含不相关的多个改动
- commit message 写 "fix bug" / "update code"
- 提交未格式化的代码
- 提交包含 TODO/FIXME 的代码到主分支
```

## 三、禁止项 (Prohibited)

### 3.1 代码层面

| 禁止项 | 原因 | 替代方案 |
|--------|------|----------|
| `catch (Exception e) {}` 空 catch | 吞掉异常，生产事故根源 | 至少 log.error()，或抛出自定义异常 |
| `catch (Exception e)` 捕获过宽 | 把 NPE 和业务异常混在一起 | 精确捕获具体异常类型 |
| `e.printStackTrace()` | 不受日志框架管理 | `log.error("msg", e)` |
| `System.out.println()` | 绕过日志框架 | `log.info/debug/warn/error()` |
| 裸 `new Thread()` | 线程不受 Spring 管理 | `ThreadPoolTaskExecutor` 或 `CompletableFuture` |
| `@Autowired` 字段注入 | 不可测试，隐藏依赖 | 构造器注入（Lombok `@RequiredArgsConstructor`） |
| `if (obj != null)` 满天飞 | 防御式编程反模式 | `Optional`、`@NonNull`、Objects.requireNonNull |
| `return null` | NPE 隐患 | `Optional`、空集合、Null Object Pattern |
| `Date` / `SimpleDateFormat` | 线程不安全、API 糟糕 | `java.time.*`（LocalDateTime 等） |
| `HashMap` 作为缓存 | 无过期、无淘汰 | Caffeine / Redis |
| `static` 变量持有可变状态 | 并发问题、内存泄漏 | Spring Bean 管理 |
| 循环中操作数据库 | N+1 问题 | 批量查询、JOIN、批量操作 |
| 事务中调 RPC / HTTP | 长事务，锁竞争 | 先调外部，再开事务；或用 MQ 解耦 |
| `@Transactional` 放在 Controller | 事务边界错误 | Service 层 |
| 数据库自增 ID 暴露到前端 | 安全 + 可枚举 | 雪花 ID / UUID |
| 明文密码/密钥写入代码 | 安全红线 | 环境变量 / Vault / 配置中心 |

### 3.2 设计层面

```
1. 禁止在循环中创建数据库连接或 HttpClient
2. 禁止不设超时的外部调用（connectTimeout + readTimeout 必须显式设置）
3. 禁止 Redis key 不使用命名空间（如: "user:session:123"，不是 "session123"）
4. 禁止 SQL 中 SELECT *（生产禁止，测试例外）
5. 禁止分页查询不去重（先 COUNT DISTINCT，再分页）
6. 禁止 REST 接口返回 Entity 对象
7. 禁止 Controller 中手写 JSON 构造
8. 禁止跨模块直接访问数据库（必须通过 RPC/HTTP API）
9. 禁止在 for/while 中执行 SQL
10. 禁止生产环境开启 SQL 日志打印全部参数（敏感数据泄漏）
```

### 3.3 依赖管理

```
1. 禁止引入没有明确版本的依赖
2. 禁止使用 SNAPSHOT 版本上生产
3. 禁止引入多个版本的同一依赖（用 Maven enforcer / Gradle resolutionStrategy）
4. 禁止使用已标记为 @Deprecated 的 API（forRemoval=true 的必须替换）
5. 禁止引入 CVE 高危漏洞版本的依赖（用 OWASP Dependency-Check）
```

## 四、错误处理模式 (Error Handling)

### 4.1 全局异常处理架构

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 4.1.1 业务异常
    @ExceptionHandler(BizException.class)
    public Result<Void> handleBizException(BizException e) {
        log.warn("业务异常: code={}, msg={}", e.getCode(), e.getMessage());
        return Result.fail(e.getCode(), e.getMessage());
    }

    // 4.1.2 参数校验异常
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValidation(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(err -> err.getField() + ": " + err.getDefaultMessage())
                .collect(Collectors.joining("; "));
        log.warn("参数校验失败: {}", msg);
        return Result.fail(ErrorCode.PARAM_INVALID, msg);
    }

    // 4.1.3 未知异常（兜底）
    @ExceptionHandler(Exception.class)
    public Result<Void> handleUnknown(Exception e) {
        log.error("未知异常", e);
        // 生产环境不要暴露异常详情
        return Result.fail(ErrorCode.SYSTEM_ERROR, "系统繁忙，请稍后重试");
    }
}
```

### 4.2 自定义异常体系

```java
// 根异常
public class BizException extends RuntimeException {
    private final int code;
    // 构造函数接收 ErrorCode 枚举
}

// 具体场景
public class UserNotFoundException extends BizException {
    public UserNotFoundException(Long userId) {
        super(ErrorCode.USER_NOT_FOUND, "用户不存在: " + userId);
    }
}

public class InsufficientStockException extends BizException {
    public InsufficientStockException(Long skuId, int requested, int available) {
        super(ErrorCode.INSUFFICIENT_STOCK,
              String.format("库存不足: skuId=%d, 需要=%d, 可用=%d", skuId, requested, available));
    }
}
```

### 4.3 错误码枚举

```java
public enum ErrorCode {

    private final int code;
    private final String defaultMsg;
    // getter...
```

### 4.4 统一响应体

```java
@Data

    private int code;
    private String message;
    private T data;
    private long timestamp;

    // 禁止直接 new Result().setData(xxx)
    public static <T> Result<T> success(T data) { ... }
    public static <T> Result<T> fail(ErrorCode errorCode, String customMsg) { ... }
    public static <T> Result<T> fail(int code, String msg) { ... }
}
```

### 4.5 外部调用错误处理（硬性要求）

```java
// ✅ 正确示例：所有外部调用必须设超时 + 重试 + 降级
@Service
@Slf4j
public class PaymentService {

    @Retryable(
        retryFor = {RestClientException.class, SocketTimeoutException.class},
        maxAttempts = 3,
        backoff = @Backoff(delay = 1000, multiplier = 2)
    )
    public PaymentResult callPaymentGateway(PaymentRequest request) {
        try {
            return restClient.post()
                    .uri(paymentUrl)
                    .body(request)
                    .retrieve()
                    .body(PaymentResult.class);
        } catch (SocketTimeoutException e) {
            log.error("支付网关超时: orderId={}", request.getOrderId(), e);
            throw new PaymentTimeoutException(request.getOrderId(), e);
        } catch (HttpServerErrorException e) {
            log.error("支付网关5xx: orderId={}, status={}", request.getOrderId(), e.getStatusCode(), e);
            throw new PaymentServiceUnavailableException(request.getOrderId(), e);
        }
    }

    @Recover
    public PaymentResult fallback(PaymentTimeoutException e) {
        // 降级：落异步任务表，后台重试
        log.warn("支付降级: 转为异步重试, orderId={}", e.getOrderId());
        paymentRetryTaskService.createRetryTask(e.getOrderId());
        return PaymentResult.pending();
    }
}
```

### 4.6 错误处理模式速查表

| 场景 | 策略 | 实现方式 |
|------|------|----------|
| 参数校验失败 | 立即返回 400 | `@Valid` + GlobalExceptionHandler |
| 业务规则不满足 | 抛 BizException 子类 | 自定义异常 + 全局处理 |
| 数据库唯一键冲突 | 转业务异常 | catch DuplicateKeyException → 抛 BizException |
| 外部 HTTP 调用超时 | 重试 3 次 + 降级 | Spring Retry + @Recover |
| 外部 HTTP 调用失败(>3次) | 降级 / 熔断 | Sentinel / Resilience4j CircuitBreaker |
| 消息队列发送失败 | 落本地事务表 + 定时补偿 | 本地消息表模式 |
| 分布式事务 | 最终一致性 | Seata AT / TCC / Saga / RocketMQ 事务消息 |
| 定时任务执行失败 | 告警 + 手动介入 | XXL-Job 失败重试 + 告警 |
| NPE / 非预期异常 | 兜底处理, 不暴露细节 | @ExceptionHandler(Exception.class) |
| 并发冲突 | 乐观锁重试 | @Version + RetryOnOptimisticLockingFailure |

### 4.7 禁止的错误处理方式

```
1. 禁止 catch 后什么都不做（空 catch 块）
2. 禁止 catch 后只打 log 然后 return null（隐藏了错误，调用方 NPE）
3. 禁止把 checked exception 悄悄吞掉（try-catch 空的）
4. 禁止在 Controller 层 try-catch 处理异常（交给全局异常处理器）
5. 禁止在 finally 块中 return（覆盖 try 中的 return 和异常）
6. 禁止在 catch 块中再抛一个新的异常时不传 cause（new XxxException(msg) 而非 new XxxException(msg, e)）
7. 禁止用异常做流程控制（比如「查不到用户就抛异常」来做分支逻辑——用 Optional）
8. 禁止对每行代码单独 try-catch——在外层统一处理
```

## 五、执行优先级

当 Claude Code 执行任何编码任务时，按以下优先级检查：

```
1. ⛔ 禁止项检查 — 是否触碰了禁止项？（最高优先级，触碰即错误）
2. 📋 命名规范检查 — 类名、方法名、URL、数据库命名是否符合规范？
3. 🏗️ 项目结构检查 — 代码放在正确的包/模块里了吗？
4. ✅ 强制规范检查 — DTO/VO 分层、参数校验、异常处理、测试是否到位？
5. 🔧 技术栈合规检查 — 是否使用了非清单内的依赖或 API？
```
